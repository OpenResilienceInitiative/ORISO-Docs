Use the [Keycloak subchart](https://github.com/OpenResilienceInitiative/ORISO-Helm/tree/3646aecbf865c6869f7a35b2491a30312561e6f5/charts/keycloak) in ORISO-Helm. It configures the realm, the proxy headers and the public hostname under `/auth`. The ingress terminates public HTTPS. The backend HTTP listener is for the chart's internal proxy path. Preserve the realm's TLS requirement and use credentials through the environment's approved secret process.

For an empty instance the chart imports the configured realm at startup. Keycloak leaves an existing realm in place during startup import. Changes to a running realm follow the chart's documented reconciliation for that setting and the operator's deployment procedure.

## Verify the HTTPS issuer

Replace the example hostname and realm with the values for the target environment. The issuer in discovery must match the configured public HTTPS URL exactly.

```bash
curl --fail --silent --show-error \
  'https://platform.example.org/auth/realms/online-beratung/.well-known/openid-configuration' | jq -r '.issuer'
```

If discovery returns the wrong scheme, host or path, check the certificate, the selected ingress, Keycloak's public hostname and forwarded headers. If it succeeds and sign-in fails, compare the client ID and redirect URI with the configured realm and inspect the Keycloak error through the approved diagnostic path.

See [Authentication and Keycloak](/en/plattform/core-systems/authentication-and-keycloak) and [Kubernetes deployment](/en/plattform/core-systems/kubernetes-deployment).
