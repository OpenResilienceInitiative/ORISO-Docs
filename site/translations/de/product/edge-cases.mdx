<Info>
Jeder Sonderfall beschreibt **Auslöser**, **erwartetes Verhalten** und **Risiko bei Fehlbehandlung**. Die meisten greifen unmittelbar Probleme aus dem Gespräch Frank↔Nikunj auf.
</Info>

## 9.1 Sonderfälle Ratsuchender

### 9.1.1 Ratsuchende schließen Tab im Warteraum

| | |
|---|---|
| **Auslöser** | Tab schließen, wegnavigieren, Netzverlust, Betriebssystemschlaf über Heartbeat-Grenze |
| **Erwartet** | Heartbeat läuft ab (~90 Sekunden) → Ticket → `Abandoned` → anonyme Keycloak-Person **gelöscht** → Ticketzeile gelöscht → Zähler für alle Nachfolgenden vermindert |
| **Risiko** | Ansammlung von „Phantompersonen“ (Franks beschriebener Fehler). Beratende sehen leere Anfragen, Warteschlange stimmt nicht. |
| **Test** | Warteraum öffnen, Tab schließen; Ticket verschwindet binnen etwa zwei Minuten aus Beratendensicht. |

### 9.1.2 Ratsuchende schließen aktiven Chat

| | |
|---|---|
| **Auslöser** | Tab während aktivem Chat schließen |
| **Erwartet** | Heartbeat verloren → Sitzung → `Paused`; ohne Fortsetzung in fünf Minuten → `Ended`; Megolm-Schlüssel Ratsuchender verloren; Beratende sehen Verlauf weiter (≤ 48 Stunden); Metadaten anonymisiert; kein erneuter Beitritt |
| **Risiko** | Beratende mit „Geistersitzung“ blockiert |
| **Test** | Aktiver Chat → Tab schließen → Beratende sehen binnen fünf Minuten „Verbindung der Ratsuchenden getrennt“ |

### 9.1.3 Ratsuchende laden Tab neu

| | |
|---|---|
| **Auslöser** | F5 / Herunterziehen zum Aktualisieren im Warteraum oder Chat |
| **Erwartet** | Neues Cookie, neues Pseudonym, neues Ticket. Altes verwaist und wird bei Heartbeat-Ablauf gelöscht. Frühere Sitzung nicht erneut betretbar. |
| **Risiko** | Identität bleibt nach Neuladen bestehen (Datenschutzverletzung) |
| **Test** | F5 im Warteraum → Pseudonym ändert sich; altes Ticket binnen ~90 Sekunden weg |

### 9.1.4 Ungültiger Live-Chat-Link (Kennung / Thema)

| | |
|---|---|
| **Auslöser** | URL manuell geändert; Stelle gelöscht; Thema deaktiviert |
| **Erwartet** | Freundliche Seite „derzeit nicht verfügbar“ mit plattformweiter Anfrage; keine anonyme Person erstellt; kein Fehlerrauschen im Protokoll |
| **Risiko** | Verwirrende 500 / 404 / leere Seite; möglicher Backend-Absturz |
| **Test** | `/live-chat/no-such-agency` aufrufen; verständliche Seite erscheint |

### 9.1.5 DSGVO-Einwilligung Nr. 2 abgelehnt

| | |
|---|---|
| **Auslöser** | Beratende nehmen an; Ratsuchende klicken „Ablehnen“ bei DSGVO der Stelle |
| **Erwartet** | Ticket → `Abandoned`; anonyme Person gelöscht; Matrix-Raum nie fertiggestellt; Beratende sehen „Ratsuchende haben abgelehnt“ |
| **Risiko** | Chat ohne Einwilligung → rechtliche Haftung |
| **Test** | Annahme → DSGVO ablehnen → Warteschlange binnen Sekunden aktualisiert |

### 9.1.7 Selbstlöschung während aktivem Videoanruf

> *Direkte Figma-Frage: „Was passiert, wenn sich eine Person während eines Videoanrufs löscht (wenn sie ihn gestartet hat)?“*

| | |
|---|---|
| **Auslöser** | Ratsuchende haben aktiven LiveKit-Anruf gestartet und klicken „Konto löschen“ / schließen Tab |
| **Erwartet** | (1) Anruf für verbleibende Beratende fortgesetzt. (2) Startrolle an nächste Beratungsperson nach `joined_at` ASC. (3) Pseudonym binnen ~90 Sekunden gelöscht. (4) Systemnachricht: *„Ein Teilnehmer hat das Gespräch verlassen.“* (5) Ohne verbleibende Beratende beendet LiveKit kontrolliert; Chat zurück auf Text. |
| **Risiko** | Eingefrorener Anruf; Identität bleibt; LiveKit-Raum verursacht unnötige Kosten. |
| **Test** | E2E: Ratsuchende starten Anruf → löschen sich → Anruf unter Beratenden bleibt; letzte Person geht → Anruf endet; Identität gelöscht. |

### 9.1.8 Selbstlöschung aus Gruppenchat

> *Direkte Figma-Frage: „Was passiert, wenn sich Ratsuchende aus einem Gruppenchat löschen?“*

| | |
|---|---|
| **Auslöser** | „Gruppe verlassen“ oder Kontolöschung im Gruppenraum |
| **Erwartet** | (1) Pseudonym sofort gelöscht. (2) Nachrichten bleiben mit *„Ehemaliger Teilnehmer“* — Inhalte E2EE, Pseudonym nicht mehr mit Keycloak verknüpft. (3) *„{pseudonym} hat den Chat verlassen.“* (4) Bei **letzter** ratsuchender Person automatische Archivierung und Information Beratender. (5) Bei weiteren Ratsuchenden normal weiter. |
| **Risiko** | Identität bleibt in Gruppe; oder Nachrichten verschwinden und Kontext wird unverständlich. |
| **Test** | E2E: eine ratsuchende Person und zwei Beratende → Ratsuchende gehen → Systemnachricht und Autorenänderung sichtbar; Gruppe bleibt. |

### 9.1.9 E-Mail-Zustimmung während Sitzung

| | |
|---|---|
| **Auslöser** | Ratsuchende ergänzen E-Mail nach Chatbeginn |
| **Erwartet** | Verschlüsselt gespeichert, nur Plattform-Admin sieht sie; Beratende nicht; erste Bestätigungsmail; künftige Benachrichtigungen als E-Mail-Kopie |
| **Risiko** | Beratende sehen Adresse irgendwo in Oberfläche |

### 9.1.10 Mehrfachversand: gelöschte Empfänger

| | |
|---|---|
| **Auslöser** | Beratende senden an „+ Sasha (ratsuchend)“, aber Sasha hat gerade getrennt |
| **Erwartet** | Server-Relay weist mit „Person nicht mehr im Raum“ ab; Kennzeichnung „Zustellung übersprungen: eine Person“. |
| **Risiko** | Inhalt bis Sashas Rückkehr zwischengespeichert → Datenschutzverletzung |

### 9.1.11 Unkenntlichmachung versehentlich entfernt

| | |
|---|---|
| **Auslöser** | Beratende klicken Augenschalter und senden ohne erneute Unkenntlichmachung |
| **Erwartet** | Vor Abschluss Bestätigung „PII-Unkenntlichmachung deaktiviert — trotzdem senden?“ |
| **Risiko** | Ratsuchende sehen auszublendenden Inhalt |

### 9.1.6 Browser ohne Cookies / stark eingeschränkter Privatmodus

| | |
|---|---|
| **Auslöser** | Cookies deaktiviert |
| **Erwartet** | Klare Anleitung: „ORISO benötigt ein Sitzungscookie. Cookies werden mit Ihnen gelöscht, wenn Sie gehen.“ |
| **Risiko** | Stiller Fehler; Ratsuchende halten System für defekt |

## 9.2 Sonderfälle Beratender

### 9.2.1 Während Übernahme offline

| | |
|---|---|
| **Auslöser** | Ticket angenommen, vor Einwilligung Nr. 2 getrennt |
| **Erwartet** | Heartbeat-Ablauf → Ticket zurück zu `Waiting`; erneut übernommen oder Ratsuchende bei zu langer Dauer gelöscht |
| **Risiko** | Verlorenes Ticket, verlorene ratsuchende Person |
| **Test** | Annehmen → Browser Beratender beenden → Ticket wieder in Warteschlange |

### 9.2.2 Zwei Beratende nehmen gleichzeitig an

| | |
|---|---|
| **Auslöser** | Dasselbe Ticket innerhalb von Millisekunden angeklickt |
| **Erwartet** | Datenbank-Zeilensperre; erste Person gewinnt → `Accepted`; zweite sieht „bereits übernommen“; kein Doppelraum |
| **Risiko** | Doppelte Matrix-Räume und Einwilligungsabfragen |
| **Test** | Nebenläufigkeit: zwei Clients rufen `POST /live-chat/accept` für dieselbe ID → einmal HTTP 200, einmal HTTP 409 |

### 9.2.3 Live-Chat während Sitzung ausschalten

| | |
|---|---|
| **Auslöser** | Verfügbarkeit während aktiver Sitzung ausgeschaltet |
| **Erwartet** | Sitzung läuft zu Ende; keine neuen Tickets; Schalter zeigt „AUS nach Ende des aktuellen Chats“ |
| **Risiko** | Ratsuchende mitten im Gespräch verwaist |

### 9.2.4 Keine Beratungsstellenzuordnung

| | |
|---|---|
| **Auslöser** | Keycloak `consultant`, aber keine `ConsultantAgency`-Zeile |
| **Erwartet** | In App **unsichtbar** (Gespräch: „ohne Beratungsstelle nicht sichtbar“); Dashboard bittet im Hinweis um Zuordnung |
| **Risiko** | Tickets erreichen Person nie; oder erscheinen, können aber nicht angenommen werden |

### 9.2.5 Supervision tritt bei

| | |
|---|---|
| **Auslöser** | `supervisor-consultant` lädt sich in kollegialen Raum ein |
| **Erwartet** | Für alle sichtbare Systemnachricht *„Supervision X zur Qualitätssicherung beigetreten“*; Prüfeintrag; Lesen erlaubt, Person in Mitgliederliste |
| **Risiko** | Stille Beobachtung → Datenschutzverletzung |

## 9.3 Sonderfälle Administration / Träger

### 9.3.1 Stelle vor Datenrichtlinienunterschrift erstellen

| | |
|---|---|
| **Auslöser** | Träger-Admin klickt „Stelle erstellen“ ohne `tenant.data_policy_signed_at` |
| **Erwartet** | Deaktiviert mit Hinweis „Zuerst Plattform-Datenrichtlinie unterzeichnen“; erzwungener Routenaufruf HTTP 403 |
| **Risiko** | Stellen ohne rechtliche Grundlage |

### 9.3.2 Zugriff auf fremde Trägerdaten

| | |
|---|---|
| **Auslöser** | URL-/API-Manipulation, JWT-Wiederverwendung |
| **Erwartet** | Trägerfilter weist auf Speicherungsebene ab (HTTP 404, **nicht** 403, gegen Informationsleck); Versuch protokolliert |
| **Risiko** | Trägerübergreifendes Datenleck — katastrophal |

### 9.3.3 Plattform-Admin deaktiviert Träger

| | |
|---|---|
| **Auslöser** | Plattform-Admin setzt `tenant.disabled_at` |
| **Erwartet** | Alle Stellen nur lesend; keine Ticketannahme; aktive Sitzungen dürfen enden; Links „derzeit nicht verfügbar“; Daten erhalten, nicht gelöscht |
| **Risiko** | Harte Abbrüche mitten im Gespräch |

### 9.3.4 Magic Link erneut verwendet

| | |
|---|---|
| **Auslöser** | Link zweimal angeklickt |
| **Erwartet** | Erstes Mal Registrierung erfolgreich, `consumed_at` in Redis; zweites Mal HTTP 410 „Link bereits verwendet“ |
| **Risiko** | Zwei Personen beanspruchen dieselbe Rolle |

### 9.3.5 Magic Link abgelaufen

| | |
|---|---|
| **Auslöser** | Klick nach 24 Stunden |
| **Erwartet** | Freundliche Ablaufseite; „Neue Einladung anfordern“ verweist auf Einladende |
| **Risiko** | Verwirrender JWT-Fehler |

## 9.4 Sonderfälle Live-Chat-Link / Pincode

### 9.4.1 Link während Seitenbesuch deaktiviert

| | |
|---|---|
| **Auslöser** | Beratungsstellen-Admin deaktiviert während Sitzung |
| **Erwartet** | Aktive Sitzungen weiter; neue Besuche „derzeit nicht verfügbar“ |
| **Risiko** | Aktive Sitzungen hart abgeschnitten |

### 9.4.2 Thema fehlt im Link

| | |
|---|---|
| **Auslöser** | Alter Link ohne `?topic=` |
| **Erwartet** | Allgemeine Stellenwarteschlange; milde Warnung; gegebenenfalls Thema erfragen |
| **Risiko** | 500 oder still falsche Zuordnung |

### 9.4.3 PLZ passt zu mehreren Stellen

| | |
|---|---|
| **Auslöser** | `10115` eingegeben; drei Stellen zuständig |
| **Erwartet** | Liste mit Beschreibungen, Ratsuchende wählen; bei Thema gefiltert |
| **Risiko** | Zufallszuordnung → falsche Beratende / Sprache |

### 9.4.4 Bot überflutet Link

| | |
|---|---|
| **Auslöser** | Curl-Schleife, Scraper, versehentliche Wiederholung |
| **Erwartet** | Ingress-Ratenbegrenzung; HTTP 429; keine Bot-Tickets für Beratende; IP-Zähler nur Arbeitsspeicher |
| **Risiko** | Echte Ratsuchende aus Warteschlange verdrängt |

### 9.4.5 Trägerübergreifender Kennungskonflikt

| | |
|---|---|
| **Auslöser** | Zwei Träger beanspruchen dieselbe Beratungsstellenkennung |
| **Erwartet** | Kennungen je Träger eindeutig; öffentliche URL enthält nur Stellenkennung; Server ermittelt Träger anhand der zugehörigen Stelle |

## 9.5 Sonderfälle Chat / Echtzeit

### 9.5.1 Netzunterbrechung während Nachricht

| | |
|---|---|
| **Auslöser** | Kurzer Ausfall bei laufender Übertragung |
| **Erwartet** | Matrix-Client versucht exponentiell verzögert erneut; nach Verbindung geordnete Ankunft; Oberfläche „wird gesendet…“ |

### 9.5.2 Schlüsselverlust (Megolm)

| | |
|---|---|
| **Auslöser** | Beratende leeren Browsercache; alte Nachrichten nicht entschlüsselbar |
| **Erwartet** | Platzhalter „verschlüsselte Nachricht — Schlüssel fehlt“; **erwartetes Verhalten** gemäß Datenschutzmodell |
| **Risiko** | System erscheint defekt; keine serverseitige Schlüsselhinterlegung erfinden |

### 9.5.3 Massive Warteschlangenüberlastung

| | |
|---|---|
| **Auslöser** | 500 gleichzeitige Ratsuchende im Warteraum |
| **Erwartet** | Redis-Zähler skaliert; Löschungen pünktlich; realistische Wartezeithinweise |
| **Risiko** | Datenbankzeilen explodieren; Bereinigung hängt; Zähler veraltet |

### 9.5.4 Matrix-Raumerstellung fehlgeschlagen

| | |
|---|---|
| **Auslöser** | Synapse vorübergehend gestört |
| **Erwartet** | UserService versucht dreimal mit Verzögerung; bei Dauerfehler Ticket zurück und klare Meldung |
| **Risiko** | Ticket aktiv ohne Raum; Ratsuchende hängen fest |

## 9.7 Betriebs- / Sicherheitsfälle

| Szenario | Erwartet |
|---|---|
| Keycloak im Entwicklungsmodus | **Harter Alarm.** Bereitstellung per CI-Sperre blockieren. Nach Vorfall 2026 bekräftigt. |
| Externer Penetrationstest zählt Sitzungen auf | IDs UUIDv4; Trägerbegrenzung macht Aufzählen nutzlos |
| Sicherungsdatei offengelegt | Pseudonyme keine personenbezogenen Informationen; Nachrichten E2EE; Mitarbeitendendaten spaltenverschlüsselt; Wirkung begrenzt |
| Realm.json weicht zwischen Entwicklung und Produktivbetrieb ab | Jährliche externe Prüfung und CI-Differenzalarm |
| MFA-Faktor verloren (Admin) | Wiederherstellung getrennt über Plattform-Admin; kein eigenständiges Zurücksetzen |

## 9.10 Übergabefälle

| Auslöser | Erwartet |
|---|---|
| B lehnt Übergabe ab | Ticket zurück in Stellenpool mit „Übergabe erforderlich“ |
| Ratsuchende lehnen ab | Sitzung kontrolliert beendet; Ratsuchende gelöscht |

## 9.11 Gruppenchatfälle

| Auslöser | Erwartet |
|---|---|

## 9.14 Sonderfälle bei der Kontowiederherstellung

### 9.14.1 Die ratsuchende Person hat ihr Passwort vergessen und keine E-Mail-Adresse hinterlegt

<Warning>
**Eine Wiederherstellung ist nicht möglich. Der Zugang zum Konto ist dauerhaft verloren.** Das
folgt aus dem Anonymitätsmodell und ist kein technischer Defekt. Bis zum 08.08.2026 war diese
Folge jedoch nirgends dokumentiert (OpenResilienceInitiative/ORISO-UserService#928).
</Warning>

| | |
|---|---|
| **Auslöser** | Anonyme Registrierung ohne E-Mail-Adresse; später kann sich die Person nicht mehr anmelden |
| **Erwartetes Verhalten** | Es gibt keinen Weg zurück in das Konto. Der `userName` (Anmeldename) ist das einzige Kennzeichen und unveränderlich; das erzeugte 16-stellige Passwort wird nach der Registrierung nicht erneut angezeigt |
| **Tatsächliche Anzeige** | Nichts erklärt diesen Umstand. Die Anmeldeseite der App bietet im Passwortmodus zwar „Passwort vergessen“ an, für dieses Konto führt der Weg aber ins Leere: Nach Eingabe des Anmeldenamens erscheint „E-Mail wurde versendet“, es kommt jedoch nie eine E-Mail an (Weg 1 unten). Die eigene Keycloak-Anmeldeseite des Realms `online-beratung` hat keinen Link zum Zurücksetzen (`resetPasswordAllowed: false`), und ein direkter `GET /realms/online-beratung/login-actions/reset-credentials` liefert Status 400; Ratsuchende sehen diese Seite aber nie, weil die App eine eigene Anmeldung hat |
| **Risiko bei falscher Behandlung** | Eine Person in einer Belastungssituation verliert unbemerkt den Zugang zu einer bereits begonnenen Beratung |
| **Test** | Anonym und ohne E-Mail-Adresse registrieren, abmelden, in der App „Passwort vergessen“ wählen und den Anmeldenamen eingeben: Die Erfolgsmeldung erscheint, es kommt keine E-Mail an, und nichts erklärt den Grund |

**Drei Wege, die den Kontozugang nicht wiederherstellen.** Sie scheitern auf unterschiedliche
Weise. Nur der erste Weg bleibt absichtlich ohne erkennbare Wirkung:

1. **Passwortzurücksetzung — ohne sichtbare Wirkung.** `PasswordResetService` versendet nichts,
   wenn die Adresse leer ist oder auf das Suffix einer künstlichen Platzhalteradresse endet.
   Genau das trifft auf anonyme Ratsuchende zu (`UserHelper`, `identity.email-dummy-suffix`).
   Die Person sieht „E-Mail wurde versendet“, erhält aber keine Nachricht. **Dieses Verhalten
   schützt bewusst davor, Konten anhand der Antwort zu ermitteln**: asynchroner Versand mit
   konstanter Laufzeit, gleiche Antwort selbst bei voller Warteschlange, keine personenbezogenen
   Daten in Logs. Es darf nicht durch eine verräterische Fehlermeldung „behoben“ werden.
2. **Magic Link — wird abgelehnt.** `validateMagicLinkTogglePrerequisites` lässt die Aktivierung
   ohne echte Adresse nicht zu. Selbst mit funktionierendem Magic Link wäre dies eine bequemere
   Anmeldung, keine Kontowiederherstellung.
3. **Matrix-Wiederherstellungsschlüssel — erfüllt einen anderen Zweck.** Er stellt den
   **Nachrichtenverlauf** wieder her, nicht den Zugang zum Konto. Beides gleichzusetzen wäre ein
   Kategorienfehler und keine Fehlfunktion.

**Ausgleichsmaßnahme und ihre Bedeutung für verschiedene Träger.** Schaltet ein Träger die
E-Mail-Einladung ab — wie U25 —, bleibt das Speichern der Zugangsdaten als **einzige**
Absicherung. Deshalb ist diese Funktion dort besonders wichtig: der Baustein `saveCredentials`
der Erstantwort (ADR-018, OpenResilienceInitiative/ORISO-Frontend#825) erscheint nach dem
Absenden der Anfrage mit einem Hinweis auf gemeinsam genutzte Geräte. Die Zugangsdaten werden
**nicht als Datei heruntergeladen**: Eine `zugangsdaten.txt` im Downloadordner wäre eine
dauerhafte Spur auf einem möglicherweise gemeinsam genutzten Gerät.

**Aktueller Stand:** Keine Wiederherstellung; das Speichern der Zugangsdaten mindert das Risiko.
Ein bei der Registrierung ausgegebener Wiederherstellungscode — nach dem Muster des vorhandenen
Matrix-Wiederherstellungsschlüssels, einmalig angezeigt und mit Bestätigung „Ich habe ihn
gespeichert“ — ist eine benannte Alternative. Er wurde **nicht inhaltlich verworfen**, aber noch
nicht beschlossen. Die Entscheidung gehört in einen eigenen Eintrag; siehe
ORISO-UserService#928.

## 9.8 Kurzübersicht „Was passiert, wenn…“

| Wenn… | Dann… |
|---|---|
| Ratsuchende verlassen Warteraum | Binnen ~90 Sekunden gelöscht |
| Ratsuchende schließen Chat | Pause; nach fünf Minuten Inaktivität Ende |
| Beratende trennen vor Einwilligung | Ticket zurück in Warteschlange |
| Zwei nehmen dasselbe Ticket an | Eine Person gewinnt, andere „bereits übernommen“ |
| Link während Sitzung deaktiviert | Aktive weiter, neue Besuche blockiert |
| Träger deaktiviert | Nur lesend; aktive Sitzungen enden regulär |
| Magic Link erneut genutzt | HTTP 410 |
| Anonymes Konto ohne E-Mail, Passwort vergessen | **Keine Wiederherstellung — der Zugang ist verloren.** Siehe §9.14.1 |
| Cookies aus | Freundliche Erklärung |
| Warteschlangenzähler widersprüchlich | Redis Pub/Sub leitet bei nächstem Ereignis erneut aus Datenbank ab |
| Ratsuchende löschen sich als Anrufstartende | Anruf unter Beratenden bleibt; Startrolle wechselt; Ratsuchende gelöscht |
