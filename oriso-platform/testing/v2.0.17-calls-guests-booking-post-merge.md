# v2.0.17 post-merge test plan: guest account modes, call start, self-booking, call fixes

Run this after the PRs below are merged into `dev` and deployed to Dev (`https://dev.oriso.org`). Every scenario is written as steps and an expected result, and says which ORISO-E2E spec covers it today or that a new spec is still needed.

Issues: [ORISO-UserService#1662](https://github.com/OpenResilienceInitiative/ORISO-UserService/issues/1662) (guest account modes), [ORISO-Frontend#2287](https://github.com/OpenResilienceInitiative/ORISO-Frontend/issues/2287) (asker calls and self-booking), [ORISO-Frontend#2307](https://github.com/OpenResilienceInitiative/ORISO-Frontend/issues/2307) (call diagnosis fixes). Decisions: ADR-029, ADR-020 and ADR-032 amendments of 2026-11-17 in `oriso-platform/decisions/`.

## Preconditions

### 1. Merged and built

All PRs above are merged into `dev`, and the CI image build of every merge commit is green. UserService carries three PRs in one image; Frontend, Element Call and the gateway carry two or three each. Deploy only once all PRs of an image are in it.

### 2. Deploy order (backend before frontend)

Run each step separately and stop on the first failure. Script names come from the Dev runbook (`RUNBOOK-dev-environment-access-and-deployment.md` in the ORISO Core); repeat `ls` on the master node before use.

1. **Helm upgrade by the Dev operator** (separate procedure, not a deploy script): ORISO-Helm#555 (UserService `startupProbe`, `readinessProbe`, `maxSurge: 1, maxUnavailable: 0`) and ORISO-Helm#547 (`matrixrtcEviction.enabled: true`). Do this first so the UserService rollouts below no longer cause 503s. Afterwards check that the image references were not reset by the upgrade.
2. `./deploy-tenantservice-dev.sh` (TenantService#368: the nine guest-mode flags).
3. `./deploy-userservice-dev.sh` (UserService#1667, #1668, #1669). Check the startup log for the Liquibase changesets `20261117_guest_account_mode_1662`, `20261117_calendar_consultation_hours_2287` and `20261117_session_appointment_request_expiry_2287`.
4. `./deploy-livekit-token-service-dev.sh` (gateway: Livekit#65 and #66). The new image must still contain `eviction.js`.
5. `./deploy-element-call-dev.sh` (ElementCall#164, #165).
6. `./deploy-admin-dev.sh` (Admin#1545).
7. `./deploy-frontend-dev.sh` (Frontend#2297, #2298, #2304) last.

## Scenarios

### A. Guest account modes (ORISO-UserService#1662)

**A1 – Three modes on a direct link.** Counsellor creates a direct link three times in the Direkteinladung dialog, "Wer darf hinein?": "Nur Gäste" (delete after the session), "Beides" (guests choose), "Nur mit Konto" (permanent). Open each link in a fresh browser context.
Expected: *delete after the session* enters without an account and the link chip reads "Temporär"; *guests choose* offers "Ohne Konto beitreten" and "Konto anlegen", chip "Gast wählt"; *permanent* requires an account. `GET /users/data` of the temporary guest shows `temporaryAccount: true`.
Covered by: **new spec needed** (no ORISO-E2E spec opens a direct link today).

**A2 – Träger cap.** Platform admin: "Gastkonten erlauben" shows three modes for chat, audio and video, all on. Switch *permanent* off for video and enforce it. Träger admin: the switch is off and locked. Träger admin: switch *guests choose* off for chat, save, reload.
Expected: the setting survives the reload; the counsellor's mode select in "Meine Direktlinks" no longer offers the disabled modes; a link created with a disabled mode falls back PERMANENT → GUEST_CHOOSES → TEMPORARY.
Covered by: **new spec needed**. `tests/group-chat-smoke.spec.ts` SG6 opens the same permission page read-only but checks only the "Gruppenberatungen" card.

**A3 – Keep the account.** Enter as a guest under *guests choose* without an account. Conversation menu → "Konto behalten", enter a password.
Expected: success message; display name and notification settings appear in the profile; the deletion job no longer removes the account. A guest who entered under *delete after the session* sees no "Konto behalten" (`temporaryAccountKeepAllowed: false`; the API answers 403).
Covered by: **new spec needed**.

**A4 – Function guard.** As a temporary guest, open the profile.
Expected: no display name, e-mail, e-mail/browser notification or password card. Direct API calls to change the display name, save an e-mail, enable e-mail notifications or register a push token answer 403; clearing stays allowed. After A3 all of them work.
Covered by: **new spec needed**.

**A5 – Group-call guest link.** A moderating counsellor of the Gesprächskreis starts an encrypted group call and opens the call menu.
Expected: "Einladelink senden" and "Link teilen" are there; a guest opens the link, knocks, is admitted and registers under the creator's Beratungsstelle. When a plain member starts the group call instead, the share button disappears after about a minute (6 polls, 404 `CALL_SHARE_LINK_NO_CALL`) and both in-call entries vanish without a reload (ElementCall#164).
Covered by: **new spec needed**.

### B. Call-start guard (ORISO-UserService#1668, ORISO-Livekit#65, ORISO-ElementCall#165)

**B1 – Advice seeker cannot start.** As the advice seeker, open the 1:1 call room while no call runs (for example the call URL from an earlier call).
Expected: the gateway answers 403 `call_start_requires_counsellor`; Element Call retries once after 2 s, then shows "Der Anruf hat noch nicht begonnen".
Covered by: **new spec needed**.

**B2 – Counsellor starts as before.** Counsellor starts a video call from the 1:1.
Expected: the call window opens and runs.
Covered by: `tests/call-branding.spec.ts` (counsellor-started call opens; command above).

**B3 – Join needs a live counsellor.** Counsellor starts the call; the advice seeker joins. Counsellor leaves, call room still open; the advice seeker tries again.
Expected: the first join works; the second is refused with the same message as B1. An admitted direct-link guest joins a counsellor's running call.
Covered by: **new spec needed**.

### C. Self-booking (ORISO-UserService#1669, ORISO-Frontend#2298)

**C1 – Sprechstunden settings.** Counsellor: calendar settings menu → "Sprechstunden", add a window (e.g. Tuesday 10–12), keep auto-accept, set notice 1 day and 60 min, save, reload.
Expected: the values come back. A counsellor who never saved settings has auto-accept **on** (default).
Covered by: **new spec needed**.

**C2 – Asker call buttons.** Advice seeker opens the 1:1.
Expected: video and audio buttons show. With an appointment, a click shows date, time and video/phone, and no call starts. Without one, "Termin anfragen" lists free times inside the Sprechstunden for 14 days. Counsellor without Sprechstunden: no free times, and a registered advice seeker sees the hint to write in the chat.
Covered by: **new spec needed**.

**C3 – Instant booking.** Book a slot outside the notice period with auto-accept on.
Expected: the appointment is scheduled, the dialog shows it, the counsellor sees it. A second booking in the same conversation answers 409 `SELF_BOOKING_LIMIT_REACHED`. Two advice seekers booking the same slot at once: exactly one wins.
Covered by: **new spec needed**.

**C4 – Request, confirm, decline.** Switch auto-accept off (or book inside the notice period). Book.
Expected: the split button shows "Angefragt · <time>"; the counsellor's "Meine Termine" shows the request dashed with "Angefragt · wartet auf Sie"; "Bestätigen" makes it a normal appointment, "Ablehnen" removes it and frees the time; the conversation gets the notice. The advice seeker can "Anfrage zurückziehen". The second counsellor does not see the request.
Covered by: **new spec needed**.

**C5 – Expiry at slot start.** Leave a request unanswered past its start.
Expected: it disappears from the calendar, the appointment list and the split button; the advice seeker can book again; within a minute the row is `DECLINED` with `expired`; opening the conversation as either person posts "Terminanfrage abgelaufen: …" exactly once.
Covered by: **new spec needed** (needs a slot that starts during the run, at least 2 h ahead because of the lead time, or a dedicated short-notice fixture).

### D. Call diagnosis fixes (ORISO-Frontend#2307)

**D1 – "Beitreten" answers a ringing call (Frontend#2304).** Counsellor starts a video call. While the advice seeker's incoming card rings, she presses "Beitreten" on the call message in the chat.
Expected: she is in the call; the ringing stops.
Covered by: **new spec needed** (`tests/call-widget-mode.spec.ts` covers a two-person call but is excluded from the `dev` project).

**D2 – Unanswered ring ends (Frontend#2304).** Counsellor calls; nobody answers.
Expected: the incoming card disappears after 60 s; the next call rings normally.
Covered by: **new spec needed**.

**D3 – No 503 during a UserService rollout (Helm#555).** Run `./deploy-userservice-dev.sh` while a counsellor starts a video call every 10 s.
Expected: the old pod stays `Running` until the new one is `Ready`; no call start answers 503.
Covered by: **new spec needed** (manual with `kubectl -n caritas get pods -w`).

**D4 – Every 503 is logged (Livekit#66).** Provoke a gateway 503 (for example during D3 without Helm#555) and read `kubectl -n caritas logs deploy/matrixrtc-auth-policy-gateway`.
Expected: one JSON line `matrixrtc_authorization_unavailable` with `step` and `upstreamStatus`, without room id, user id or token.
Covered by: **new spec needed**.

### E. Eviction (ORISO-Helm#547, already merged)

**E1 – Revoked guest leaves the call.** Counsellor admits a direct-link guest into a running call, then revokes the guest's seat.
Expected: within a few seconds the guest is removed from the LiveKit call; the UserService log shows no `Call eviction was not confirmed`.
Covered by: **new spec needed**. Blocked until the Helm#547 values are applied (see the 2026-11-17 state above).

**E2 – Banned group member leaves the call.** Ban a member of a Gesprächskreis while they are in its group call (ORISO-Admin#1518).
Expected: the member is removed from the call.
Covered by: **new spec needed**; same Helm precondition.
