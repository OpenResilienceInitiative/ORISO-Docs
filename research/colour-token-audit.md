# Colour tokens: what already exists, and what the code really backs

Research for [ORISO-Docs#145](https://github.com/OpenResilienceInitiative/ORISO-Docs/issues/145) (child of map [#144](https://github.com/OpenResilienceInitiative/ORISO-Docs/issues/144)).
Read-only audit, measured 2026-10-02 after `git fetch --all --prune` in every repo.

Scope walked: Dev branch first (`origin/dev` of Frontend `1154ca44`, Admin `4faddc30`, TenantService `1c9ef3e`, UserService `3c5e089a4`, Docs `3fbfd32`, ElementCall `fff6dfc9`), then local worktrees, stashes and unpushed branches, then remote branches and PRs (open, closed, merged). Deployed Dev was **not** probed: every "on dev" below means "on the `origin/dev` branch", not "running on dev.oriso.org".

Method note for readers who re-check: `git ls-tree`, `git grep <pattern> origin/dev -- <path>` and `git show origin/dev:<path>` in each repo reproduce every path:line below; PR/issue facts come from `gh issue view` / `gh pr view`.

## 1. Verdict in five lines

1. **The colour engine, the runtime palette, the Träger seed storage and the platform to Träger inheritance are real and merged on `origin/dev`.** `EffectiveThemingApplier` exists and works the way the ticket assumes (see section 4).
2. **ADR-010 is largely plan only.** Its data model (`appearanceAllowedTenantIds`), its "hide instead of read-only" rule and its Global Settings multi-select are not in the code. A different mechanism (per-tenant permission policy) enforces the permission instead. The ADR itself has been `Proposed` since import and was never updated.
3. **There are two colour engines.** The Frontend runs the real Material Color Utilities engine (408 lines + tuning file). The Admin runs a hand-written 332-line copy without the library and without `orisoTuning.ts`. Details belong to [#147](https://github.com/OpenResilienceInitiative/ORISO-Docs/issues/147); here it is only recorded as a fact.
4. **High contrast does not exist in the app or in the Admin.** No `prefers-contrast` rule in any Frontend or Admin source on any ref (pickaxe over `--all`). The only product decision is [Frontend#1134](https://github.com/OpenResilienceInitiative/ORISO-Frontend/issues/1134) (optional personal mode, planned v2.0.13). Element Call's generated sheet has no `-hc` block.
5. **The most valuable unmerged work is Frontend PR [#1528](https://github.com/OpenResilienceInitiative/ORISO-Frontend/pull/1528)** (open, 97 files): a `--oriso-primary-text` token that steps a too-light Träger colour down its own tonal palette. Nothing equivalent is on `dev`, in the Admin, or in mail.

## 7. Gaps and limits of this audit

- Deployed Dev (image tags, `curl` of the running bundle) was not probed; "merged" always means on the `origin/dev` branch. Admin#905 and TenantService#174 have Dev-deployment questions that stay open on their tickets.
- Slack and Figma were not read; the Figma state is taken from the comment on [Frontend#901](https://github.com/OpenResilienceInitiative/ORISO-Frontend/issues/901).
- Hex counts are line counts from `git grep`; a `var(--m3-x, #hex)` fallback line is counted in the fallback figure, not in the bare figure. They size the problem; the real mapping is [#146](https://github.com/OpenResilienceInitiative/ORISO-Docs/issues/146).
- Opacity and disabled patterns ([#148](https://github.com/OpenResilienceInitiative/ORISO-Docs/issues/148), [#154](https://github.com/OpenResilienceInitiative/ORISO-Docs/issues/154)), the exact Admin vs Frontend palette diff ([#147](https://github.com/OpenResilienceInitiative/ORISO-Docs/issues/147)) and the screenshot method ([#149](https://github.com/OpenResilienceInitiative/ORISO-Docs/issues/149)) are other tickets of the map and were only touched where they decide a status here.
